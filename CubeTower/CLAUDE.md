# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

CubeTower is a Unity game where the player taps to stack cubes onto a wobbling tower. A blinking "ghost" cube shows candidate placements; the player taps to commit. Physics on the stack decides the loss condition (if the tower's rigidbody starts moving, the player has lost).

- **Unity version:** `2022.3.62f3` (see `ProjectSettings/ProjectVersion.txt`). Open the project with exactly this editor — `.csproj` / `.sln` files in the repo root are regenerated by Unity on open and should not be hand-edited.
- **DI framework:** Zenject is vendored in `Assets/Plugins/Zenject/`. As of the current branch (`feature/BigRefactoring`) it is **installed but not yet wired up** — no installers, no `SceneContext`, no `[Inject]` usages in `Assets/Scripts/`. The refactor in progress is the thing that will introduce DI; keep this in mind before assuming Zenject is already in use.

## Build / run

This is a Unity project with no CLI build scripts. Everything goes through the Unity Editor:

- **Play/iterate:** open `Assets/Scenes/Main.unity` and press Play. It is the only gameplay scene.
- **Build:** File → Build Settings in the editor. There is no headless/CI build pipeline checked in.
- **Tests:** no test assemblies exist under `Assets/` — only Zenject's own integration/unit tests ship under `Assets/Plugins/Zenject/OptionalExtras/`, and those target Zenject itself, not game code. Do not treat Zenject's tests as project tests.

## Code layout (what to read first)

All gameplay lives in `Assets/Scripts/` — it is small (≈6 files) and worth reading end-to-end before making changes:

- `GameController.cs` — the game loop. Holds the authoritative list of occupied cube positions (`_allCubesPosition`), runs `ShowCubePlace` as a coroutine that randomly repositions the ghost cube among empty neighbors, handles tap-to-commit in `Update`, and drives camera follow + background color tinting as the tower grows.
- `CubePos.cs` — integer-vector struct used to track the "current top cube" position. Note: positions in `_allCubesPosition` are stored as `Vector3` (floats) even though the grid is integer — `IsPositionEmpty` compares with `==`, which works only because values are whole numbers set from integer sources.
- `ExplodeCubes.cs` — attached to the ground collider. When the tower's parent cube collides with the ground, it re-parents each child cube, adds a Rigidbody + explosion force, and shows the restart button. This is how the "lose" visual is produced.
- `Rotate.cs` — spins a transform on Y (used for the start-screen prop).
- `CanvasButton.cs` — UI hookups (restart scene, open an Instagram URL).
- `Core/MainMono.cs` — empty `MonoBehaviour` subclass in namespace `Core`. Most gameplay scripts inherit from it instead of `MonoBehaviour` directly. It's a seam for the upcoming Zenject refactor; don't delete it or bypass it when adding new gameplay scripts in this branch.

### Architectural quirks to be aware of

- **Two parallel "lose" paths.** `GameController.Update` sets `_isLose` when `_allCubesRb.velocity.magnitude > 0.1f` (stack moved). `ExplodeCubes.OnCollisionEnter` independently reacts to a cube hitting the ground. They don't talk to each other. Changing one without the other will desync the lose state.
- **`SpawnPosition` dead branch.** The final `else` after `positions.Count == 0` is unreachable — `Count` is either `> 0` or `0`. Preserve behavior unless the user is explicitly fixing this.
- **Camera movement is split across two systems.** `GameController.MoveCamera` nudges the camera back (`-Z`) every 3 horizontal cubes, and `ExplodeCubes` *also* nudges `-Z` on loss. Both mutate `Camera.main.transform` directly rather than going through a camera controller.
- **Scene-wired dependencies.** `GameController` exposes many `[SerializeField]` references (`cubeToPlace`, `cubeToCreate`, `allCubes`, `canvasStartPage[]`, `bgColors[]`, `mainCam`). These are all set in `Main.unity` / `Main Cube.prefab` — code changes that rename or remove these fields will silently break the scene until the prefab/scene is re-saved from the editor.

## Working in this repo

- **Do not edit `.csproj` / `.sln` / `Library/` / `Temp/` / `obj/`.** They are generated by Unity. Meta files (`*.meta`) next to every asset are required — never delete or rename an asset without its `.meta`, or references in scenes/prefabs will break.
- **Scenes and prefabs are YAML but are not meant to be hand-edited** for anything beyond trivial search-and-replace. Reference rewiring belongs in the Unity editor.
- **Platform macros.** `GameController.Update` has a `#if !UNITY_EDITOR` block that gates touch-phase handling — behavior in the editor and on-device is intentionally different there. Test both when touching input code.
